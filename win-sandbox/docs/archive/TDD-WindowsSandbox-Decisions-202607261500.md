## 2. 背景与目的

HLD 已经在宏观层面完成了架构分层、模块分解、接口定义。但若干关键技术决策点存在多个候选方案，每个方案在隔离强度、实现复杂度、部署门槛、性能开销上各有取舍。本 TDD 针对这些决策点逐一对比，给出推荐方案与理由，作为 LLD 阶段的输入。

本 TDD 覆盖以下 8 个决策点：

| ID | 决策点 | 影响 LLD |
|----|--------|----------|
| D1 | 隔离技术栈组合 | LLD-01/02/05 |
| D2 | 文件系统写重定向方案 | LLD-05 |
| D3 | 网络拦截方案 | LLD-06 |
| D4 | 行为监控方案 | LLD-07 |
| D5 | IPC 通道与序列化 | LLD-04 |
| D6 | IPC 消息 schema 演进策略 | LLD-04 |
| D7 | 部署形态（子进程 vs 服务化） | LLD-08 |
| D8 | Python 包发布形式 | python/ |

约束前提（来自 PRD，不再讨论）：

- 仅 Windows 10 1809+，x64
- 用户态可达上限，不引入需要驱动签名的内核组件
- 自适应权限（普通用户/管理员双模式）
- C++17 + CMake + WIL + nlohmann::json + spdlog

## 3. D1：隔离技术栈组合

### 3.1 候选方案

#### 方案 A：Job Object + AppContainer（HLD 推荐）

**描述**：Job Object 管资源（CPU/内存/IO/进程数/UI），AppContainer 管访问控制（文件/注册表/网络/IPC），二者通过同一 Token + 同一 Job 协同。

**优点**
- 资源限制与访问控制分离，职责清晰
- 纯用户态，无驱动签名要求
- AppContainer 默认拒所有，安全基线高
- 多实例独立 Job + 独立 Profile，互不干扰

**缺点**
- AppContainer 不能限制 CPU/内存，必须依赖 Job
- Job 不能阻止文件访问，必须依赖 AppContainer
- 部分高级能力（CPU Rate Control v2、IO Rate Control）需 Win10+ 且管理员

**适用场景**：PRD 全部场景（OJ/REPL/样本分析/CI）

#### 方案 B：Server Silo（进程隔离容器）

**描述**：使用 Windows 10 1709+ 的 Server Silo（Pico 进程 / Silo Job），把被隔离进程放入独立 Silo，享有独立文件系统视图、注册表视图、进程列表。

**优点**
- 隔离强度最高，接近轻量虚拟化
- 文件系统/注册表重定向由内核支持，无需用户态 hack

**缺点**
- 部分核心 API 未文档化（如 NtCreateJobObject 的 Silo 标志）
- 创建 Silo 需要 SeTcbPrivilege，等价于系统权限
- Profile/容器镜像管理复杂，类似 Windows Container
- 与 Python 子进程编排模型不匹配（Silo 内进程对宿主不可见）

**适用场景**：需要强隔离的样本分析（可接受高复杂度）

#### 方案 C：Hyper-V Container / WSL

**描述**：每个沙箱实例启动一个轻量虚拟机或 WSL 发行版。

**优点**
- 隔离强度最高，硬件级
- 微软官方支持，API 稳定

**缺点**
- 启动慢（秒级到十秒级）
- 资源占用大（每实例 GB 级内存）
- 与"Python 细粒度编排"诉求不匹配
- WSL 仅 Linux 二进制，不适合 Win32 沙箱

**适用场景**：长期运行的服务化沙箱（非本项目目标）

### 3.2 对比表

| 维度 | A: Job+AppContainer | B: Server Silo | C: Hyper-V/WSL |
|------|---------------------|----------------|----------------|
| 隔离强度 | 中高 | 高 | 最高 |
| 实现复杂度 | 中 | 高 | 低（调 API）但运维重 |
| 启动延迟 | <1s | 1-3s | 5-30s |
| 内存占用 | <50MB | 100-500MB | GB 级 |
| 驱动签名 | 不需要 | 部分需要 | 不需要 |
| 文档完整度 | 完整 | 部分 | 完整 |
| Python 编排友好度 | 高 | 中 | 低 |
| Win10 1809+ 可用 | 是 | 是（受限） | 是 |
| 普通用户可用 | 部分（自适应降级） | 否 | 否 |

### 3.3 推荐方案

**采用方案 A（Job + AppContainer）**，将 Server Silo 列为 Phase 2 候选（仅当 PRD 场景 C 样本分析需要更强隔离时评估）。

**理由**
1. 满足 PRD"用户态可达上限"约束。
2. 启动延迟、内存占用、Python 编排友好度全面优于 B/C。
3. AppContainer + 路径白名单 + WFP + ETW 已经覆盖 PRD 全部隔离维度。
4. Server Silo 的文档缺口与特权要求会显著拖慢 M1-M7 进度。

## 4. D2：文件系统写重定向方案

### 4.1 候选方案

#### 方案 A：NTFS Junction + 路径白名单（HLD 推荐）

**描述**：在临时工作区创建到原工作目录的 Junction（或符号链接），通过 GrantSidAccess 授予 AppContainer SID 对 Junction 目标的写权限。被隔离程序看到的路径不变，但实际 IO 落在临时区。

**优点**
- 纯用户态，无需驱动
- Junction 对应用程序透明，无需修改程序
- 实现简单（CreateSymbolicLink / DeviceIoControl FSCTL_SET_REPARSE_POINT）

**缺点**
- Junction 是目录级，文件级重定向需复制
- 跨卷 Junction 有限制（仅同卷本地路径）
- 被隔离程序用 GetFinalPathNameByHandle 可能看穿真实路径

**适用场景**：PRD 场景 A/B/D，场景 C 的轻量样本

#### 方案 B：Minifilter 驱动

**描述**：注册文件系统微过滤驱动，在 IRP_MJ_CREATE / IRP_MJ_WRITE 阶段重定向到沙箱临时区。

**优点**
- 文件级精细重定向
- 完全透明，应用程序无法察觉
- 支持跨卷

**缺点**
- 需要驱动签名（EV 证书 + WHQL）
- 安装需管理员/重启
- 开发复杂度高（C/C++ 内核编程）
- 违反 PRD"用户态上限"约束

**适用场景**：强隔离样本分析（如 Sandboxie）

#### 方案 C：用户态 API Hook（DLL 注入）

**描述**：向被隔离进程注入 DLL，hook CreateFileW/WriteFile 等 API，在用户态重定向路径。

**优点**
- 纯用户态
- 文件级精细

**缺点**
- 仅 hook 本进程，子进程需重新注入
- x64 下 hook 复杂（PatchGuard、CFG）
- 被隔离程序可绕过（直接 syscall）
- 注入本身需要权限，与 AppContainer 冲突

**适用场景**：不推荐

#### 方案 D：复制工作目录 + 路径白名单

**描述**：启动时把工作目录复制到临时区，被隔离程序工作目录设为临时区，不重定向。

**优点**
- 实现最简单
- 完全隔离

**缺点**
- 大目录复制慢
- 不是"重定向"，被隔离程序看到的路径就是临时区路径（不透明）
- 程序硬编码绝对路径会失效

**适用场景**：PRD 场景 A（OJ 评测，工作目录小）

### 4.2 对比表

| 维度 | A: Junction | B: Minifilter | C: API Hook | D: 复制 |
|------|-------------|---------------|-------------|---------|
| 透明度 | 中高 | 高 | 中 | 低 |
| 文件级粒度 | 否（目录级） | 是 | 是 | 是（间接） |
| 用户态实现 | 是 | 否 | 是 | 是 |
| 驱动签名 | 不需要 | 需要 | 不需要 | 不需要 |
| 实现复杂度 | 低 | 高 | 中 | 极低 |
| 跨卷支持 | 否 | 是 | 是 | 是 |
| 子进程覆盖 | 是 | 是 | 否 | 是 |
| 抗逃逸 | 中 | 高 | 低 | 高 |
| 启动开销 | 极低 | 低 | 低 | 高（取决于目录大小） |

### 4.3 推荐方案

**默认采用方案 A（Junction + 白名单）**，提供方案 D（复制）作为 `temp-workspace` 模式的退化实现，方案 B（minifilter）列为 Phase 2 评估项（开放决策 O1）。

**理由**
1. 方案 A 满足"用户态上限"，对程序透明，启动开销极低。
2. 跨卷限制通过配置约束（要求临时区与原目录同卷）规避。
3. 方案 D 在小工作目录场景下更简单可靠，作为配置选项保留。
4. 方案 B 的驱动签名门槛超出当前阶段资源。

**配置策略**：
- `fs.mode = combined`（默认）：方案 A
- `fs.mode = temp-workspace`：方案 D
- `fs.mode = whitelist`：仅白名单，无重定向
- `fs.mode = redirect`：方案 A（Phase 2 升级为方案 B）

## 5. D3：网络拦截方案

### 5.1 候选方案

#### 方案 A：WFP 用户态 ALE Callout（HLD 推荐）

**描述**：注册 FWPM_LAYER_ALE_AUTH_CONNECT_V4/V6 用户态 callout，拦截 connect 调用，按白名单放行/拒绝。

**优点**
- 用户态可注册，无需驱动签名
- 拦截点在应用层，可获取进程上下文（PID、目标 IP:port）
- 微软官方支持，API 稳定

**缺点**
- 用户态 callout 有超时限制（默认 30s，可配置），超时按策略放行/拒绝
- 仅拦截 connect，不拦截已建立连接的 send/recv
- 高并发下 callout 队列可能成为瓶颈

**适用场景**：PRD 场景 A/B/D，场景 C 的网络日志

#### 方案 B：WFP 内核态 Callout 驱动

**描述**：注册内核态 WFP callout，在 FWPM_LAYER_OUTBOUND_TRANSPORT_V4 等层拦截。

**优点**
- 性能最高（无用户态切换）
- 可拦截所有层（包括 send/recv）

**缺点**
- 需要驱动签名
- 内核编程复杂度高
- 违反 PRD"用户态上限"约束

**适用场景**：高性能场景（不推荐）

#### 方案 C：LSP（Layered Service Provider）

**描述**：注册 Winsock LSP，拦截所有 socket 调用。

**优点**
- 用户态
- 可拦截 send/recv

**缺点**
- 微软已废弃（Win10 起不推荐）
- 仅拦截 Winsock，不拦截 raw socket / WinINET
- 影响整个系统稳定性

**适用场景**：不推荐

#### 方案 D：命名管道代理 / SOCKS 代理

**描述**：沙箱内置 SOCKS5 代理，被隔离程序配置走代理，沙箱按白名单转发。

**优点**
- 纯用户态，无 WFP
- 实现简单

**缺点**
- 需要被隔离程序支持 SOCKS（很多程序不支持）
- 不透明，需要修改程序配置
- 拦截不到非 SOCKS 流量

**适用场景**：被隔离程序可控且支持代理

### 5.2 对比表

| 维度 | A: WFP 用户态 | B: WFP 内核 | C: LSP | D: SOCKS 代理 |
|------|---------------|-------------|--------|---------------|
| 用户态实现 | 是 | 否 | 是 | 是 |
| 驱动签名 | 不需要 | 需要 | 不需要 | 不需要 |
| 拦截范围 | connect | 全部 | Winsock | SOCKS 流量 |
| 透明度 | 高 | 高 | 中 | 低 |
| 性能开销 | 中 | 低 | 高 | 中 |
| 现代性 | 是 | 是 | 否 | 是 |
| 微软推荐 | 是 | 是 | 否 | N/A |

### 5.3 推荐方案

**采用方案 A（WFP 用户态 ALE Callout）**，提供方案 D（SOCKS 代理）作为 `network.policy = proxy` 模式的实现。

**理由**
1. 方案 A 是唯一同时满足"用户态 + 透明 + 微软推荐"的方案。
2. 拦截 connect 已足够覆盖 PRD 场景（OJ 禁网、样本分析日志、白名单放行）。
3. callout 超时通过配置控制（默认 100ms，超时按 `network.timeout_action` 放行或拒绝）。
4. 方案 D 作为补充，处理需要应用层代理的特定场景。

## 6. D4：行为监控方案

### 6.1 候选方案

#### 方案 A：ETW 内核会话 + 用户态 Provider（HLD 推荐）

**描述**：启动 ETW 实时会话，启用 NT Kernel Logger（进程/线程/镜像/文件/注册表）、Kernel-Network（TcpIp/UdpIp）、Kernel-File 等 provider，通过 EventRecordCallback 接收事件。

**优点**
- 内核态事件，权威且低开销
- 跨进程监控，无需注入
- 微软官方支持
- 单 session 可订阅多 provider

**缺点**
- ETW 事件格式复杂，解析麻烦
- 高频事件下可能丢事件（需 ring buffer）
- 部分 FileIo 事件路径解析需要二次查询（OpenID → FileName）

**适用场景**：PRD 全部场景

#### 方案 B：API Hook（DLL 注入 + Detours）

**描述**：向被隔离进程注入 DLL，hook CreateFileW/RegCreateKeyEx 等 API。

**优点**
- 事件格式可控（直接拿到参数）
- 可修改行为（如改变返回值）

**缺点**
- 仅 hook 本进程，子进程需重新注入
- x64 hook 复杂
- 与 AppContainer 冲突（注入需要权限）
- 抗逃逸弱

**适用场景**：不推荐

#### 方案 C：Minifilter + RegFilter 驱动

**描述**：注册文件系统微过滤驱动 + 注册表过滤驱动。

**优点**
- 内核态，最权威
- 可修改行为

**缺点**
- 需驱动签名
- 违反"用户态上限"

**适用场景**：强隔离场景（不推荐）

### 6.2 对比表

| 维度 | A: ETW | B: API Hook | C: 驱动 |
|------|--------|-------------|---------|
| 用户态实现 | 是 | 是 | 否 |
| 跨进程监控 | 是 | 否（需注入子进程） | 是 |
| 抗逃逸 | 高 | 低 | 高 |
| 事件丰富度 | 中（依赖 provider） | 高 | 高 |
| 性能开销 | 低-中 | 中-高 | 低 |
| 实现复杂度 | 中 | 中 | 高 |

### 6.3 推荐方案

**采用方案 A（ETW 内核会话）**，对于"句柄打开"等 ETW 不直接提供的事件，降级为 ETW + AppContainer 拒绝事件（AccessDenied 触发时记录）。

**理由**
1. 方案 A 是用户态可达的最强监控方案。
2. AppContainer 拒绝事件天然补充了"敏感访问"日志，无需 hook。
3. 方案 B/C 违反约束或抗逃逸弱。

**Session 分流策略**（缓解单 session 瓶颈）：
- Session 1：NT Kernel Logger（进程/线程/镜像）
- Session 2：FileIo + Registry
- Session 3：TcpIp + UdpIp

每个 session 独立 ProcessTrace 线程 + 独立 ring buffer。

## 7. D5：IPC 通道与序列化

### 7.1 候选方案

#### 方案 A：命名管道 + 长度前缀 + JSON（HLD 推荐）

**描述**：命名管道作为传输层，每帧格式为 `[4字节小端长度][UTF-8 JSON]`，使用 nlohmann::json 序列化。

**优点**
- Windows 原生，安全描述符可控
- JSON 可读，调试友好
- 跨语言友好（Python 标准库即支持）
- nlohmann::json header-only，集成简单

**缺点**
- JSON 解析开销高于二进制协议
- 大消息（如 stdout 块）base64 编码膨胀 33%

**适用场景**：控制面消息、事件流

#### 方案 B：本地 TCP + Protobuf

**描述**：本地 loopback TCP，protobuf 二进制序列化。

**优点**
- 性能高
- 强类型 schema

**缺点**
- 占用端口，防火墙可能干扰
- protobuf 需要 codegen，构建复杂
- 跨语言需要生成 Python stub

**适用场景**：高频 IPC

#### 方案 C：stdin/stdout JSON Lines

**描述**：沙箱进程 stdin 接收命令、stdout 输出事件，每行一条 JSON。

**优点**
- 实现极简
- 跨语言

**缺点**
- 双向能力弱（stdin 只能发命令，stdout 只能发事件）
- 无法多客户端
- 与沙箱进程自身的日志输出冲突

**适用场景**：简单一次性运行

### 7.2 对比表

| 维度 | A: 命名管道+JSON | B: TCP+Protobuf | C: stdin/stdout |
|------|------------------|------------------|------------------|
| Windows 原生 | 是 | 否 | 是 |
| 多客户端 | 是 | 是 | 否 |
| 双向交互 | 是 | 是 | 弱 |
| 安全描述符 | 是（DACL） | 否（靠端口） | 否 |
| 性能 | 中 | 高 | 中 |
| 调试友好 | 高 | 低 | 高 |
| 构建复杂度 | 低 | 高 | 极低 |
| 跨语言 | 是 | 是 | 是 |

### 7.3 推荐方案

**采用方案 A（命名管道 + JSON）**。

**理由**
1. 命名管道是 Windows 原生 IPC，DACL 可控，满足安全设计。
2. JSON 调试友好，Python 端零依赖。
3. 大消息（如 stdout 块）的 base64 膨胀通过分片缓解（每片 ≤ 64KB）。
4. 性能瓶颈不在 IPC（PRD 目标 ≤ 10000 events/s，命名管道+JSON 实测可达 50000+）。

## 8. D6：IPC 消息 Schema 演进策略

### 8.1 候选方案

#### 方案 A：硬编码消息类型 + 版本字段

**描述**：在协议头携带 `version` 字段，消息类型用枚举硬编码在 C++ 和 Python 两端。

**优点**
- 实现简单
- 类型安全（编译期检查）
- 零运行时开销

**缺点**
- 协议升级需要双端同步发布
- 不支持动态 schema 发现

**适用场景**：单一项目、版本可控

#### 方案 B：Schema Registry（动态 schema）

**描述**：沙箱启动时通过 IPC 广播 schema 列表，客户端按 schema 解析消息。

**优点**
- 支持动态发现
- 跨版本兼容性好

**缺点**
- 实现复杂
- 运行时开销
- 对静态语言（C++）不友好

**适用场景**：多版本共存、插件化

#### 方案 C：JSON Schema 校验

**描述**：消息仍是硬编码类型，但用 JSON Schema 做运行时校验。

**优点**
- 兼顾简单与校验
- schema 可作为文档

**缺点**
- 运行时校验开销
- JSON Schema 库依赖

**适用场景**：需要严格校验的场景

### 8.2 对比表

| 维度 | A: 硬编码+版本 | B: Registry | C: JSON Schema |
|------|-----------------|-------------|----------------|
| 实现复杂度 | 低 | 高 | 中 |
| 类型安全 | 编译期 | 运行时 | 运行时 |
| 跨版本兼容 | 弱 | 强 | 中 |
| 性能 | 高 | 中 | 中 |
| 调试友好 | 中 | 低 | 高 |

### 8.3 推荐方案

**采用方案 A（硬编码 + 版本字段）**，方案 C 作为可选校验层在 Debug 构建启用。

**理由**
1. 单一项目，C++ 与 Python 同步发布，无需动态发现。
2. `version` 字段足够处理不兼容升级（拒绝旧版本客户端）。
3. 新增消息类型是后向兼容的（旧客户端忽略未知 type）。
4. JSON Schema 校验在 Debug 构建启用，Release 构建关闭以提升性能。

**版本策略**：
- `version = "1.0"`：初始版本，覆盖 M0-M8 全部消息
- `version = "1.x"`：新增消息类型或字段（后向兼容）
- `version = "2.0"`：破坏性变更（如字段重命名、语义变更），客户端必须升级

## 9. D7：部署形态

### 9.1 候选方案

#### 方案 A：Python 子进程（HLD 推荐）

**描述**：每个 Python 进程通过 subprocess.Popen 启动一个沙箱实例，沙箱随 Python 进程退出而退出。

**优点**
- 部署简单（沙箱 = 一个 exe）
- 资源隔离清晰（一 Python 一沙箱）
- 故障隔离（沙箱崩溃不影响其他）
- 与 Python 习惯一致

**缺点**
- 多 Python 进程共享同一沙箱需要额外机制
- 启动开销（每次启动沙箱进程）

**适用场景**：PRD 全部场景

#### 方案 B：Windows Service

**描述**：沙箱作为 Windows 服务常驻，多个 Python 客户端通过命名管道连接。

**优点**
- 多客户端共享
- 启动开销分摊
- 服务可自动重启

**缺点**
- 部署复杂（需安装服务）
- 服务通常以 SYSTEM 运行，安全风险高
- 多客户端隔离需要额外设计
- 与 AppContainer Profile 隔离模型冲突

**适用场景**：多客户端共享场景

#### 方案 C：混合模式

**描述**：默认子进程模式，可选配置为连接已有服务。

**优点**
- 灵活
- 兼顾两种场景

**缺点**
- 实现复杂度翻倍
- 测试覆盖困难

**适用场景**：长期演进

### 9.2 对比表

| 维度 | A: 子进程 | B: Service | C: 混合 |
|------|-----------|------------|---------|
| 部署复杂度 | 低 | 高 | 高 |
| 多客户端共享 | 否 | 是 | 可选 |
| 启动开销 | 高 | 低（已启动） | 取决于模式 |
| 故障隔离 | 强 | 弱 | 中 |
| 安全风险 | 低 | 高（SYSTEM） | 中 |
| 实现复杂度 | 低 | 中 | 高 |

### 9.3 推荐方案

**M0-M8 采用方案 A（子进程）**，方案 B/C 列为 Phase 2 候选（开放决策 O3）。

**理由**
1. 子进程模式与 Python 编排模型最匹配。
2. 故障隔离强，沙箱崩溃不影响 Python 主进程。
3. AppContainer Profile 每实例独立，与子进程模式天然契合。
4. 服务化引入的多客户端隔离问题需要重新设计 Job/AppContainer 边界，超出当前阶段范围。

## 10. D8：Python 包发布形式

### 10.1 候选方案

#### 方案 A：Wheel 包 + 沙箱 exe 数据文件

**描述**：打包成 wheel，沙箱 exe 作为数据文件随包发布，安装时复制到 site-packages。

**优点**
- 标准 pip 安装
- 版本管理清晰
- 跨 Python 版本兼容

**缺点**
- exe 需要预编译多版本（Python 3.8/3.9/3.10/3.11/3.12）
- 实际上 exe 与 Python 版本无关（仅依赖 Windows API），wheel 元数据需声明平台

**适用场景**：标准 Python 包分发

#### 方案 B：单文件 zipapp

**描述**：打包成 .pyz 单文件，沙箱 exe base64 内嵌或随 zip 携带。

**优点**
- 单文件分发
- 无需安装

**缺点**
- exe 内嵌base64 增大体积
- 启动时需解压
- 不支持版本管理

**适用场景**：便携场景

#### 方案 C：源码安装

**描述**：用户克隆仓库，自行编译沙箱 exe，pip install -e . 安装 Python 包。

**优点**
- 灵活
- 无需预编译

**缺点**
- 用户需 C++ 编译环境
- 部署门槛高

**适用场景**：开发者

### 10.2 对比表

| 维度 | A: Wheel | B: zipapp | C: 源码 |
|------|----------|-----------|---------|
| 安装便利 | pip install | 解压即用 | 需编译 |
| 版本管理 | 强 | 弱 | 强 |
| 用户门槛 | 低 | 低 | 高 |
| 平台标记 | platform-specific | 通用 | 通用 |
| 体积 | 中 | 大 | 小 |

### 10.3 推荐方案

**M0-M7 采用方案 C（源码安装）**，M8 切换为方案 A（Wheel）正式发布。

**理由**
1. 开发期源码安装便于快速迭代。
2. M8 阶段功能稳定后，构建 wheel（标记 `platform = win_amd64`、`python-version = py3`）分发。
3. 方案 B 的便携性优势在本项目不显著（用户主要是开发者）。

**Wheel 构建**：
- `pyproject.toml` 声明构建依赖
- `setup.py` 或 `hatchling` 配置
- `package_data` 包含 `bin/sandbox.exe`
- CI（GitHub Actions）自动构建并发布到 PyPI 或 GitHub Release

## 12. 风险与缓解

| 决策 | 风险 | 缓解 |
|------|------|------|
