## 关键发现（重要，防止重踩）
1. **conhost.exe 会进入 Job 并产生事件**：控制台应用启动时 Windows 创建
   conhost.exe（父进程 = 控制台主进程），未 breakaway 的 Job 会收到它的
   NEW_PROCESS/EXIT 通知。因此事件流中**永远不要假设"第一个 job_process_started
   就是业务子进程"**——e2e 断言必须按 `process_name` 过滤（或 exit_code 等特征）。
2. **已退出进程的退出码查询窗口**：进程对象在退出后仍存活短暂窗口
   （console 子系统等持有引用，实测 ≥100ms，之后 OpenProcess 返回 err=87 →
   `query_failed`）。需要"已退出进程的退出码"时必须在退出事件后**立即查询**；
   entry 本身在 CleanupFinished（仅 StartProcess/TerminateProcess 命令前调用）前
   一直存活，不受此窗口影响。
3. **崩溃路径去重复用既有 `exited_pids_`**：ABNORMAL_EXIT(8) + EXIT(7) 双通知
   已在 JobObjectImpl IocpLoop 去重，usecase 层无需新增去重。e2e T9-5 验证
   crash_dummy 崩溃只发一条 `job_process_exited`（exit_kind=abnormal, 0xC0000005）。

## 黑盒复核（2026-08-10，外部委托测试 REPORT.md 复查）
- 委托方黑盒测试产物 `tests/e2e/blackbox_phase9/`（bb_groupA/BC/DE/F/S），
  复跑后三项处置：
  1. **F9 修复**：`query_process_exit_code` 的 pid/process_id 校验从
     `is_number()` 收紧为 `is_number_integer()`（main.cpp 两处）。nlohmann
     `get<int>` 对 double 静默截断（1234.5 → 1234），float 此前被接受 →
     契约违背。e2e T9-10 回归。
  2. **B5 修复**：`JobObjectImpl::QueryProcessExitCode` 增加 Job 归属校验
     ——`seen_pids_`（NEW_PROCESS 通知登记，含主进程 Assign 时、已退出进程；
     mutex 保护，IocpLoop 写/查询线程读）+ `IsPidInJobAlive`
     （JobObjectBasicProcessIdList 活进程兜底，覆盖通知未处理的竞态窗口）。
     pid 不属于本 Job → `ProcessNotFound`（process_not_found）。跨 sandbox
     实例探测、系统 pid（如 1）均被拒绝；B2（已退出子进程，对象已回收）仍
     query_failed；B3（主进程退出后窗口内）行为不变。e2e T9-11 回归，
     8a 期望更新（0x7FFFFFFF → process_not_found）。
  3. **A1a 误报**：黑盒初版 3 层嵌套命令 `cmd /c "cmd /c \"...\""` 中 `\"`
     不是 cmd.exe 的转义引号——内层带引号部分被当作程序名 →
     "不是内部或外部命令"（exit_code=1），实际只创建 1 层子进程。
     修正命令（去掉内层引号）`cmd /c cmd /c cmd /c timeout /t 3` 复跑：
     **4 层进程树完整上报**（main→cmd→cmd→timeout），parent_pid 逐级正确，
     `total_processes=5` 与事件数吻合，无遗漏。**黑盒脚本命令构造问题，
     非监测缺陷**。

  `stats_report` 为周期事件（~1.1s/条），队列永不为空 → 空转满
  total_timeout（A 组 121s → 修正为"主进程退出时刻+窗口"后 13s）。

- 教训：Windows cmd 嵌套命令的引号规则与 bash 不同（无 `\"` 转义），

  类退出条件，尾部窗口应基于时间而非队列状态。
