## 2. 目标

实现网络隔离，支持 4 种策略（deny-all / allowlist / proxy / full）。结束时被隔离进程的网络访问可被拦截、白名单放行、事件回传。能跑通 PRD 场景 C 的网络部分。

---

## 3. 范围

### In Scope
- `IWfpEngine` 接口 + `WfpEngineImpl`
- WFP 用户态 ALE callout 注册（`FWPM_LAYER_ALE_AUTH_CONNECT_V4/V6`）
- 4 种网络策略：
  - `deny-all`：不授予网络 Capability，AppContainer 默认拒
  - `allowlist`：WFP callout 按白名单放行/拒绝
  - `proxy`：内置 SOCKS5 代理转发器
  - `full`：授予 `internetClient`，不限制
- `NetworkRule` 实体（IP、port、protocol）
- `NetworkBlocked` 事件（目标 IP:port、协议、拒绝原因）
- WFP callout 超时处理（默认 100ms）
- 配置项：`network.policy`、`network.allowlist`、`network.proxy`、`network.timeout_ms`、`network.timeout_action`

### Out of Scope
- WFP 内核态 callout（TDD D3 已拒绝）
- LSP（已废弃）
- 网络流量内容日志（仅记录 connect 事件，Phase 6 ETW 补充）

## 8. 实现记录（2026-07-31）

### 重大设计变更：放弃 WFP，改用 AppContainer capability

原计划使用 WFP 用户态 ALE callout 实现网络拦截。实际实现时发现：
1. WFP 需要管理员权限注册 callout，与 Phase 7 自适应降级目标冲突
2. AppContainer 本身已提供网络隔离能力（通过 capability 控制）
3. 可通过 `PrepareAppContainer` 根据 `net_policy` 追加不同 capability 实现策略分级

因此 Phase 5 网络隔离改为 **capability-based** 方案：

| 策略 | Capability | 说明 |
|------|------------|------|
| `None` (deny-all) | 不追加 | AppContainer 默认拒绝所有网络 |
| `LoopbackOnly` | `privateNetworkClientServer` | 仅 loopback（但平台限制无法实际访问 loopback）|
| `Outbound` | `internetClient` | 出站连接 |
| `Unrestricted` | `internetClient + internetClientServer` | 全部网络 |

### 平台限制发现

1. **AppContainer 无法访问本地 loopback**：即使授予 `privateNetworkClientServer` capability，AppContainer 内进程仍无法连接 loopback。这是平台限制，非 capability 解决。因此 loopback 测试改为仅验证 capability 配置正确，不验证实际连接。
2. **非管理员无法对系统目录写 ACL**：AppContainer + DefaultDeny 模式对 `C:\Windows\System32` 等系统目录写 ACL 需要管理员权限。测试改用 `temp_workspace` 模式绕过。
